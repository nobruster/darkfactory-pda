01The boot camp.

FIVE EVENINGS · FOUR HOURS A DAY · LIVE · ONE CONTINUOUS BUILD

Agentic Engineering in Practice is a five-day, four-hours-a-day live boot camp (19h30–23h30) in which each student builds a complete agentic system on their own laptop: a factory that migrates a legacy payment-processing data platform — the NorthWind Pay EDP — to a modern open-source stack, and proves the migration correct cent by cent against the running legacy. It is not a course about agents. It is the supervised construction of an agentic factory, one evening at a time, until the human steps out of the execution path.

The promise

In five days, you will not learn to use agents — you will build a complete agentic system, from zero to production, that migrates a legacy financial platform by itself, validates itself against the past, and repairs itself for the future. 02The reason.

THE MIGRATION THAT NEVER STARTS · THE QUESTION THAT FREEZES IT · THE RULER THAT SITUATES YOU

Every large enterprise runs a NorthWind Pay: a transaction core that works, that nobody fully understands, and that nobody dares to touch. The board wants the migration. The budget — twelve to eighteen months of a full team — has been approved twice and started zero times. It always freezes on the same question: who guarantees the new system's numbers match the old one's, cent by cent?

The real risk was never the system going down. It is the system working and being wrong: a swapped offset, an inverted sign in a COBOL overpunch byte — and plausible-but-wrong money is born, the kind no test catches and that only surfaces three months later in an audit. Plausible is not correct. The answer to the frozen question is not more people. It is a factory that treats the legacy — with all its defects — as the oracle, and validates every translation against it.

The week begins inside the chaos every legacy migration actually starts with: meeting transcripts, Slack threads, half-true BRDs, scattered documentation. The Archaeologist's job is to turn that chaos into context a machine can reason over — before writing a single line of the new system.

  • Inject the chaos into Claude Cowork: transcripts, threads, BRDs, loose legacy docs — the real raw material of understanding.
  • Build the project's Second Brain — Cowork + Obsidian + MCP automations + Schedules: a living organism that keeps itself updated. The day's "wow": every student leaves with a self-feeding second brain of the project.
  • Run OntoLayer over the legacy Postgres — crawl → enrich → serve: ~300 stored procedures plus schema become a navigable knowledge graph instead of illegible DDL, with safe text-to-SQL via sqlglot. Without the ontological base you cannot see how the legacy connects.

  • Pass 1 · Intent: the material condenses into a tech-spec that answers the brief.
  • Pass 2 · Structure (brownfield): OntoLayer answers supply the facts; transcripts endorse each decision; both become ADRs — facts and constraints, never "how to build".

  • Activate the Loop (task-runner --issue N) — the first time with no HITL: read task-spec + ADRs + harness → branch → code → run the eval. RED feeds the failure back and revises; GREEN opens the PR that closes the issue. Convergence is a green eval, never a number of attempts.

  • The Wall: generator and validator never share context — the structural mitigation against sycophancy.

THE AHA — GOLDEN-MATCH AUDITS THE ORACLE

The golden-match compares the old PL/pgSQL against the new Python side by side, cent by cent. On one batch the declared control total reads 173.44 — while the Java, the PostgreSQL SQL, and the new Python all independently compute 173.45. The factory does not "fix" anything: it preserves the declaration byte-exact, classifies the divergence CONFIRMED_SOURCE_DEFECT, quarantines the batch, and lets its neighbors through. The old system was right the whole time — its inputs were not. The golden-match exists because a wrong money number goes unnoticed; this is the moment the room never forgets, and the reason Eval Engineering is not optional in a financial system.

The vocabulary and the harness.

SEAM → SWIMLANE → LEG → TASK-SPEC · EACH MODEL IN ITS ROLE
1
Seam

The system's natural joint — where it already wants to be cut, like the seams of a shirt, never mid-fabric. Canonical: transform (medallion raw→bronze→silver→gold) vs serve (API/MCP over gold). Cut at the published contract, above implementation detail.

2
Swimlane

The work lane born from each seam — one lane, one plan, one focus. It passes the deep-lane test: a consumer can say what it does, how to use it, and what it depends on without reading its internals.

3
Leg

The stretch inside a lane that is too big — named swimlane-{seam}-leg-{NN}-{tech}. "Leg" as in a relay race: each swimmer swims one leg of the lane. Each leg yields 1:N task-specs.

4
Task-Spec

The atomic unit with an eval — the thing an agent executes. Behavior, contract, guardrails, operations, ≥3 runnable evals, retry policy, dependencies, and a seal. No eval, not a task.

08The modern use case.

WHAT THE FACTORY BUILDS · EVENT-DRIVEN → LAKEHOUSE → SERVING · VALIDATED CENT BY CENT

The modern platform replaces the Java black box and the ingestion procedures with one data-driven, event-driven Python function per file type, and the black-box business rules with a governed medallion lakehouse. The same approved raw bytes flow through — never re-touched, never reinterpreted at will.

raw .dat/.txt arrives → the factory takes over EVENT-DRIVEN PYTHON one function per file type — model → parser → schema → writer anonymizes PII (kills the Java) · parses the layout (kills ingestion SQL) deterministic, atomic PARQUET · money is Decimal, never float │ ▼ dlt → DUCKLAKE + DUCKDB table format + analytical engine — the local lakehouse │ ▼ dbt MEDALLION BRONZE typed, source-aligned, never re-parses ▸ SILVER conforms — changes no monetary value ▸ GOLD governed reconciliation at the legacy reporting grain │ ▼ DAGSTER assets + lineage → FASTAPI + MCP — ask in natural language, the data answers │ ▼ GOLDEN-MATCH every number compared cent by cent against the running legacy oracle

Golden-match — the release gate with no tolerance knob

Every comparison asks two questions — legacy parity and business correctness — and classifies every difference as exactly one of CONFIRMED_SOURCE_DEFECT, CONFIRMED_LEGACY_DEFECT, MODERN_DEFECT, APPROVED_BEHAVIOR_CHANGE, CONTRACT_AMBIGUITY, or UNRESOLVED. The release gate permits no unexplained financial difference, and no tolerance setting exists anywhere — a configurable tolerance is how an unexplained cent becomes an accepted cent. Rejected batches are compared on terminal behavior — status, stable code, zero output, peer continuation — never on rows.

THE RATIO IS THE POINT

6,834 vs 29,622 lines

The modern side implements the same five types in ~23% of the legacy's line count. The difference is not cleverness — it is the absence of accumulated compensation.

PROOF SHAPE

Gates, not vibes

20 dbt models · 131 data tests · 87 unit tests · Dagster assets with checks · every model and test tagged per type, because an untagged test silently never runs.

NORTHWIND PAY EDP AS IT STANDS · THIRTY FILE TYPES · THREE HUNDRED PROCEDURES · ONE BLACK BOX

NorthWind Pay processes transactions: cards clear, instant payments land, slips settle — and each cycle the core drops 30+ raw file types onto an SFTP: positional .dat, proprietary-layout .txt, COBOL overpunch, PII in the clear. Between the SFTP and the database sits a Java system nobody wants to touch — it reads the raw file, anonymizes PII, tokenizes cards, and emits a sanitized CSV. Only then do ~300 PL/pgSQL stored procedures apply the business rules that close the day. The tangle grew over 3–4 years and 8–12 departing developers; the business rules live inside the procedures; every new file type is risky surgery.

WHY THE MIGRATION CAN BE PROVEN · THE DOCTRINE THE WHOLE WEEK RESTS ON

The factory never "trusts" a translation: it validates every number against the legacy running side by side. And when a divergence appears, the new system is not always wrong — sometimes the legacy's inputs were wrong all along, preserved byte-exact by every faithful implementation downstream. That inversion is the defining moment of Day 4: the factory audits the oracle, classifies what it finds, and never silently repairs.

DOCTRINE · 1

No oracle, no build

A specification that does not ship its expected outputs cannot be adjudicated — the factory refuses it before doing any work.

DOCTRINE · 2

A gate that cannot fail is worse than no gate

It spends your attention and gives nothing back. Six vacuous gates were found and closed in this estate — four by the autonomous run, two by human review. Prove a new gate red before you accept it green.

DOCTRINE · 3

The golden is evidence, not truth

The raw bytes plus the specification are truth; the legacy, with all its defects, is the oracle; an oracle is evidence — never license to edit an expected value to force green.
