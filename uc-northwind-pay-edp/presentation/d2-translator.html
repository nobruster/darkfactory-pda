Two plants

Same drop. Different destinations.

One batch lands on SFTP and both plants read it. Java keeps posting CSV to the books, tonight and every night. java2py, once the owner signs, writes Parquet to a landing zone that does not exist yet.

Mixing destinations is a failed day. Java never writes Parquet. Python never writes CSV — and never writes anything back to SFTP.
Event-driven · why

The architecture is event-driven because the business is

Nothing calls the plant. There is no API to subscribe to, no queue to poll. At 02:14 a batch file appears on SFTP — and that landing is the event. Everything downstream exists because one file showed up, and every property we need falls out of that.

01
The trigger is a fact, not a guess
A file landing in raw/incoming is the moment money arrived. No scheduler polling at 02:00 hoping the batch is there.
02
One batch is one unit of work
Sense it, claim it exactly once, emit once. The batch id is the idempotency key — a retry cannot double-post.
03
Refusal is a valid ending
An event may end as refused: trailer 173.44 vs rows 173.45. Nothing half-written, no Parquet on reject.
04
Isolation by construction
Each drop is independent. A Type 02 failure never touches Type 01’s batch — peers continue, the bad one is quarantined.
05
Replay is byte-identical
Re-emit the same file, get the same Parquet. The audit trail is the list of events — the graph and the books can be rebuilt from it.
06
No always-on plumbing
One drop a night is not traffic. No broker to babysit, no consumer lag — the filesystem is the queue, and it is already there.
not Kafka not a bus not a cron guess Dagster will orchestrate this event on Day 4 — it does not replace it. Tonight’s seam is sense → claim → emit.
